# MyToken 双端迭代复盘（2026-09-08 ~ 09-09）

> 覆盖范围：macOS 菜单栏客户端（SwiftUI / AppKit）与 Android 客户端（Jetpack Compose）
> 两天的密集迭代：小组件与 OEM 兼容、滚动性能、菜单栏闪退、弹窗尺寸、更新系统重做
> （CDN 通道 / 弹窗 / 系统通知 / 检测修复）、UI 设计语言统一、发布体系治理。
> 目标读者：后续项目开发者。每条经验都对应本仓库真实发生的事故或决策。

## 0. 三条最重要的话

1. **真因未验证前，不动架构。** vivo 小组件事故中连续做了三个"修复"
   （替换 RemoteViewsService、移除 configure Activity、调整自动更新周期），全部无效，
   真因只是布局 XML 里一个 `?attr` 主题属性引用。每一步无效修复都在消耗用户信任、
   制造回滚成本，最后还要把误删的功能逐个恢复。
2. **客户端内置逻辑无法被远程修复。** 更新检测器打进每个安装包里，仓库侧改代码
   触达不了存量安装。发布形态（tag 方案）的任何变更，都必须先兼容所有已发客户端
   的旧解析逻辑，并准备发布侧的迁移兜底（本次：旧 macos-v 发布转草稿）。
3. **高频回调必须有去重。** 菜单栏图标闲置闪退的根因，是邻居状态项每次刷新都让
   AppKit 重设按钮 appearance、反复触发 KVO 重绘，高频文字测量撞上 CoreText 竞态。
   "状态没变就跳过"这一行判断就是最终修复。

## 一、产品设计

### 1.1 版本号与发布形态是产品决策
- 事故：主 CI 发布 `v5.1.x` tag，检测器只认 `macos-v5.1.x` 前缀且取列表首个匹配，
  最新匹配停留在 5.1.9 → 5.1.10 以上的用户全部检测不到更新。
- 结论：发布 tag 方案是"客户端检测器"的数据契约。改发布流程 / 新增 tag 前缀前，
  先审计所有在野客户端版本的解析逻辑；发布形态尽量单一、稳定。
- 衍生：GitHub Releases 的列表排序是黑盒（观察到的顺序既非时间也非纯版本序），
  不要把"用户从列表第一个找到最新版"当作功能依赖；引导用户看 App 内更新与
  仓库首页的 Latest 标记。

### 1.2 大陆网络可达性是一等公民
- GitHub API 与 release 下载在大陆不稳定。更新通道做成显式配置
  （直连 / CDN 加速 + 多镜像可切换）：镜像前缀改写 `github.com` URL（下载 / 发布页 /
  Atom 检测），API 直连失败自动回退镜像 Atom。
- 结论：镜像站可用性会波动，"多源可切换"比"单一可靠源"更现实；配置要持久化并在
  每次检测/下载时实时读取。

### 1.3 触发后台动作的控件必须有反馈闭环
- Android 小组件刷新、macOS 刷新按钮原先点击无反馈，用户无法感知是否触发。
- 结论：开始要有即时反馈（降透明度 / 旋转动画），完成要有终止反馈（绿色对勾 /
  恢复常态），失败要有明确错误。反馈与动作在同一上下文里闭环
  （更新弹窗内嵌下载进度，而不是把进度丢在页面别处）。

### 1.4 存量用户迁移要有可逆的兜底动作
- 旧检测器用户升级依赖"手动下载一次"。把旧 `macos-v5.1.7/8/9` 发布转为草稿后，
  老客户端扫描到的第一个平台发布变成最新版本，一次性把卡住的用户全部解救。
- 结论：优先选**可逆**的发布侧操作（转草稿 > 删除），并明确告知用户哪些版本
  需要手动跳一次。

### 1.5 主题不是单一状态
- 用户会跟随系统在明暗间切换。所有新控件（玻璃按钮/开关/输入框/chip）明暗两套
  都要验证对比度与可见性：浅色玻璃用黑色系细描边才有边界，深色用白色高光描边。
- 强制亮色的场景（更新确认弹窗）要显式 `environment(\.colorScheme, .light)`，
  并自定文字色，避免深色模式下弹窗内容不可读。

### 1.6 双端功能对等与平台差异化并行
- 核心数据（凭证 / 用量 / 提醒）双端一致；平台能力各取所长：
  macOS 菜单栏常驻 + 状态栏多图标，Android 桌面小组件 + 系统分享/安装器。
- 迁移体验（扫码 + 端到端加密）是双端粘合点，文案要明确"密钥不经过第三方"。

### 1.7 文案可操作、信息脱敏
- 错误文案给可操作指引（"去授权"直达系统设置），不暴露密钥与内部细节；
  检测失败类错误统一"请稍后重试"，不泄露原始异常。

## 二、业务逻辑

### 2.1 版本比较 = 解析 + 比较 + 选择，三层都要防御
- tag 前缀混用（`v` / `macos-v` / `android-v`）：解析层统一剥离前缀取 semver；
  比较层逐段数值比较；选择层"全部候选取版本最大"，**不要**"列表第一个匹配"
  （依赖 GitHub 的黑盒排序）。
- 回归测试覆盖真实发布形态：v + android-v + macos-v 混合列表，必须选中正确的
  平台最新版本（仓库内有现成用例可参考）。

### 2.2 更新提醒按版本去重并持久化
- 每 6 小时一轮检测（启动后立即先查一轮），同一版本重复发系统通知会打扰用户。
  按版本号写 UserDefaults 去重（跨启动生效）；通知未授权时自动补一次授权请求。

### 2.3 校验前置，快速失败
- Android 发布工作流在构建前用 keytool 逐项校验签名（文件头 / store 密码 /
  alias / key 密码），签名配置错误 5 秒内报出来，而不是 6 分钟构建失败后。

### 2.4 发布资产命名是接口约定
- Atom 兜底路径不含资产列表，按命名约定（`MyToken-{version}-arm64.dmg` 等）
  逐个 HEAD 探测。命名约定变更 = 破坏旧客户端的探测逻辑。

### 2.5 刷新与提醒策略全部用户可配、默认保守
- 刷新间隔（1/5/15/30 分钟）、仅 Wi-Fi、启动刷新、失败重试、提醒开关、
  低/高阈值（默认 50/80，校验 low < high）均独立可配；阈值按 Key 独立存储。

### 2.6 数据失败的降级路径
- 刷新失败保留上次成功数据并标记 stale；Key 失效不阻塞其他 Key；
  删除 Key 联动清理缓存 / 通知状态 / 排序记录。

## 三、架构与技术选型

### 3.1 双端技术栈及原因
| 端 | 选型 | 原因 |
| --- | --- | --- |
| macOS | SwiftUI 为主 + AppKit 兜底 | 菜单栏（NSStatusItem）、弹窗（NSPopover）、系统通知必须 AppKit；内容层 SwiftUI 开发效率高 |
| Android | 单 Activity + Jetpack Compose | 声明式 UI 与 SwiftUI 心智一致；多模块（core / core-ui / data / domain / provider / feature-*）按页面拆分 |
| DI | 手写 AppGraph / AppEnvironment | 项目规模下比引入框架更直接可控，构造依赖一目了然 |
| 数据 | Room + DataStore (Android)；UserDefaults + 自建 Store (macOS) | 平台标准，均经 repository 接口暴露，UI 不直连 |
| 后台 | WorkManager (Android)、Task 调度器 (macOS) | 刷新 / 更新检查 / 检测任务统一调度 |

### 3.2 单向数据流
- StateFlow（Android）/ @Observable（macOS）→ UI state → 用户事件 → ViewModel →
  repository/service。UI 不直连数据层；测试用 Fake store 替换。

### 3.3 客户端内置逻辑不可远程升级
- 检测器 / 解析器打进安装包。发布形态变更前，先列出所有在野客户端版本的解析
  行为差异表（本次实际列了 ≤5.1.8 / 5.1.9 / 5.1.10–5.1.14 / 修复后 四代行为），
  再决定是改客户端还是用发布侧兜底。

## 四、控件选型与设计系统

### 4.1 统一为自绘"液态玻璃"控件，原因有三
1. **设计语言统一**：底部 Tab 栏已确立 LiquidGlassSurface 语言，散落的 Material
   Button / Switch / Chip（默认填充与绿系 secondaryContainer）与整体视觉割裂。
2. **单一来源**：主题推导（明暗）、强调色、无障碍、hover/press 全部集中在
   core-ui 一处，改一处全局生效。
3. **Material 组件定制成本高**：Switch 换轨道样式需要多层 overlay，自绘更可控。

### 4.2 控件清单与选择原因
| 控件 | 选择 | 原因 / 注意 |
| --- | --- | --- |
| 按钮 | 自绘 GlassButton（胶囊 + 渐变玻璃 + 同色描边），Primary/Neutral/Destructive 三色调 | Primary 只给区块主操作；破坏性统一 error 色；明暗底色透明度分别调 |
| 开关 | 自绘 GlassSwitch（胶囊轨道 + animateDpAsState 滑块） | 必须保留 Role.Switch + contentDescription（无障碍与测试依赖）|
| 输入框 | LiquidGlassSurface 外层 + 保留 OutlinedTextField 内核 | 编辑行为（密钥遮罩 / trailing 图标 / IME / testTag）不回退，只换皮；testTag 要落在输入框本体（落在容器上 RequestFocus 语义丢失）|
| 进度条 | Canvas 自绘 | LinearProgressIndicator 多一层绘制节点，OriginOS 滚动掉帧优化点 |
| Chip | 保留 FilterChip、只换配色 | M3 默认选中态是绿系 secondaryContainer，与品牌蓝冲突；统一为 primary 玻璃选中态 |
| macOS 弹窗按钮 | 自绘 GlassIconButton（hover/press 全自控） | 系统按钮在弹窗内热区只有图标；自绘后整框可点 + hover 反馈 |
| macOS 设置窗口按钮 | 系统 `.glass` 样式（macOS 26+） | 系统 hover 内建，不自绘（双轨维护成本高）|

### 4.3 代价与注意
- 自绘控件需要手工维护无障碍语义与测试 tag 落点（本次踩过两处）。
- 系统 / 自绘双轨并存：OS 升级后要回归验证系统样式是否变化。

## 五、平台兼容与性能

- **OEM 矩阵**：小米正常 ≠ vivo 正常。OriginOS 的已知差异：布局 inflate 上下文、
  后台 service 绑定限制、overscroll 行为、进程清理激进度。发布前 vivo + 小米
  真机过一遍核心路径（含小组件添加）。
- **滚动性能（真机验证有效）**：关闭拉伸 overscroll、HorizontalPager 预合成、
  Canvas 自绘进度条、裁剪玻璃层、页面级状态收集 + Eagerly。
- **性能参数必须真机 A/B**：`beyondViewportPageCount` 从 1 改 0 反而让 Tab 横滑
  卡顿（相邻页现编），改回 2 消失。单测无法覆盖这类体验。
- **用户侧系统设置引导**：后台高耗电、锁后台，是 OEM 兜底文档的必备部分。

## 六、测试与 CI

- **源码断言测试**：适合防"关键能力丢失"，但断言点选语义符号（函数名 / 关键字），
  不要断言代码结构（三元表达式改成 if/else 就挂）。重构导致断言失效时，
  同一 PR 内更新断言是正常流程。
- **异步测试等待终态**：`first { it !is Checking }` 会先匹配初始 Idle（竞态：
  CI 必挂、本地偶过）。等待 Available/Error/UpToDate 这类终态，并给 withTimeout。
- **本地过 ≠ 全量过**：DataStore 等单例状态跨测试共享，隔离跑通过、全量跑失败。
  提交前跑全模块 `gradlew test`；测试尽量不直连真实 DataStore（接口 + Fake）。
- **性能 / OEM 兼容**无法单测覆盖：打 debug 包给用户真机验证后再提交。

## 七、发布方式与策略

### 7.1 macOS：主 CI 自动 + 手动工作流双发
- **主 CI（master 推送自动）**：版本 bump 后自动构建 DMG → 发布 `v{X.Y.Z}` tag
  （Latest）→ 修复无需等手动发布即可触达全量用户。
- **手动 workflow_dispatch**：输入版本号 + 更新说明（Markdown，人工撰写），
  同 run 内发两个 release：
  - `v{X.Y.Z}`（主发布，Latest=true）——新客户端 / 首页入口；
  - `macos-v{X.Y.Z}`（Latest=false）——平台索引，兼容两代检测器。
- **为什么双发布**：存量客户端检测器分两代（macos-v 前缀世代与 v/macos-v 通吃世代），
  双发布保证任何一代检测器都能命中；代价是列表出现重复条目（可接受）。
- **为什么 workflow 构建而不是本地打包**：可追溯（run 记录 headSha = 构建源 commit，
  本次排查"5.1.15 是否包含检测修复"直接靠它确认）、环境一致、资产自动挂载。

### 7.2 Android：手动 workflow_dispatch
- 输入 versionName（建议与 macOS 主版本对齐）+ versionCode（独立递增）+ 说明；
  签名校验前置；发布前跑全模块测试。

### 7.3 测试包与正式包分离
- 大 UI 改动先打 debug 包给用户真机验证，确认后再提交 / 发版（本次验证有效，
  避免了错误方向上的多次发布）。

### 7.4 latest 标记策略
- 主发布（v tag）带 Latest=true，平台索引 release 一律 false；仓库首页 Latest
  即"当前推荐版本"。

## 八、排查方法论（本次全部实战验证）

1. **崩溃先读 .ips**：`exceptionReason` + `lastExceptionBacktrace` 直接给出
   崩溃帧、异常类型和消息（"attempt to insert nil object from objects[0]"），
   比猜测快一个数量级。
2. **数据验证假设**：检测不到更新 → 直接拉 GitHub API 看 release/tag/资产的真实
   形态与顺序，而不是从代码推断"应该没问题"。
3. **本地复现 CI 失败**：先隔离跑单个测试复现，改完先单测再全量。
4. **新旧崩溃栈对比**：修复不彻底时，对比第二份崩溃栈与第一份的调用链差异，
   能暴露真实触发路径（本次：defer 路径的栈直接否证了"传播期"假设）。
5. **多视角模拟**：认证 / 未认证请求对比（草稿可见性）、不同 startingState 的
   复现对比（竞态只在 CI）、commit 考古对比（各版本内置检测器形态），把"视角"
   当成排查变量。

## 九、协作流程

- **大 UI 改动**：改完 → 本地 debug 包 → 用户真机验证 → 提交。避免在错误方向上
  堆提交（本次性能优化与玻璃控件均按此流程执行）。
- **commit 信息写结论**而非文件清单，方便日后考古（本次多次回溯 commit 确认
  各版本内置的检测器形态）。
- **用户提问先答根因**：即使修复已推送，也要把"为什么"讲清楚（本次闪退两轮、
  检测失败一轮，用户对根因的追问都反过来推动了更准确的定位）。
- **错误诊断要留档**：三个无效修复的过程不要从记忆里抹掉，复盘时"弯路"往往
  比直路更有参考价值。

## 十、遗留风险与观察项

1. GitHub Releases 列表排序黑盒未完全掌握：macos-v5.1.16+ 在列表中的检出位置
   需观察（本轮实测 macos-v5.1.15 已可被旧客户端命中，机制应稳定）。
2. Android connected test（真机 / 模拟器仪表化测试）未接入 CI。
3. 泛 OEM（OPPO / 华为 / 荣耀等）未做真机覆盖，风险与 vivo 同类。
4. macOS 26 系统 `.glass` 按钮与自绘控件双轨并存，OS 升级后需回归系统样式。
5. 5.1.15 之前安装的用户仍需一次手动更新（已通过 macos-v5.1.15 发布 + 草稿兜底
   最大化触达，但检测器在旧包内，无法 100% 保证）。
